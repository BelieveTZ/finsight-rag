## 2. 首版使用场景

用户从预置列表选择一份英文财报，输入英文问题。系统在该文档的完整可用正文中检索，展示答案、支持答案的证据片段和 PDF 页序，并允许打开对应原文页。信息不足时说明无法从当前文档回答。

典型问题包括：某年度披露的收入数值、某项经营风险、某项业务事实。需要复杂会计判断、跨文档推理或多步计算的问题不作为首版必需场景。

可先提供中文界面，但正式基准评测保留英文原题和英文回答。中文提问、翻译及跨语言检索如增加，须单列为扩展实验。

## 5. 数据规则

### 5.1 来源与选样

采用 [FinanceBench 官方公开样本](https://github.com/patronus-ai/financebench)及对应财报作为起点。官方仓库提供 150 条公开标注样例、标准答案、证据及文档信息；本项目的评测应明确称为选定子集评测，不能代表完整 FinanceBench。

- 建议标准规模：选取 6–10 份可获得、可提取文本的英文财报，组成不少于 30 道有答案问题的固定子集。
- 选样前先检查问题与文档分布。按预先记录的文档可用性、问题类型和基础推理难度选择，不依据系统答题表现筛题。
- 入库的是选中文档的完整可用正文，不得只导入标准证据页。标准答案与证据标注只能供评测使用，不能成为检索语料或生成提示的额外输入。
- 记录数据集版本或提交号、题目 ID、文档 ID、公司、报告期、来源 URL、文件校验值，以及排除项与原因。
- 使用前检查数据和原文的许可、引用与再分发条件；公开可访问不等于可任意再分发。无法确认原文再分发权时提供来源和获取方式。
- 一旦评测集合冻结，任何更改都应产生新数据版本，并说明是否影响已有结果。

### 5.2 划分与页码

- 建议将 30 道题分为约 10 道开发题、20 道最终评测题，优先按文档隔离两组；数量受实际分布影响，需在实验前固定并公开。
- 开发题用于调试切分、检索参数、提示和拒答策略；最终评测题在配置冻结后运行。
- 两组文档均可按同一流程建立索引，但最终评测标签不得用于调参。看过最终结果后再调整配置，应将结果注明为探索性，并另留未用于调参的问题验证。
- 保存原始标注页码和内部页码的映射。FinanceBench 的 evidence_page_num 从 0 开始，展示的 PDF 页序从 1 开始；印刷页码如有则另列，不能混用。
- 解析失败、空页、表格内容损坏应记录并抽查；不得为了好看的指标静默忽略相关题目。

### 5.3 自建无答案集合

- 额外准备至少 10 道无答案问题，由人工核对在各自指定文档中缺少足够证据。
- 无答案是相对于指定文档而言，不是相对于模型知识或其他公司报告。
- 集合应在最终运行前固定，并覆盖至少缺失指标、错误报告期和超出文档范围的询问；避免只用明显无关的问题。
- 将这些问题与 FinanceBench 原始有答案题分开统计，并保留核验理由。开发与最终评测用途分别标记。

## 6. 实验与指标

### 6.1 公平对比

标准首版比较 A：纯向量检索，B：BM25 + 向量融合，C：B + 重排。记录融合方法、候选数、模型和所有关键参数。

对比使用相同文档、数据划分、切分、生成模型和提示；统一最终证据数量及上下文预算。重排可使用更大的候选池，但必须记录该差异和额外耗时。一次对比只改变明确记录的因素。

真实模型服务、预算和硬件确认后选择具体模型。首版不预先绑定供应商；测试桩的结果不能计入真实效果评测。

### 6.2 必报指标

| 指标 | 计算与报告规则 |
| --- | --- |
| 证据页 Recall@5 / @10 | 将前 K 个检索片段映射到唯一文档与页序，与标准证据页集合比较；逐题计算命中标准页数 / 标准页总数后取平均 |
| 首个证据页 MRR@10 | 前 10 个片段中首次命中标准证据页的排名倒数，未命中计 0；须说明它只评价首次命中 |
| 答案正确率 | 对有答案题按固定规则人工核对；数值需核对年份、单位、币种、量级与允许的舍入；文本需核对关键事实 |
| 引用支持率 | 逐条核对引用是否支持所关联的事实，报告支持引用条数 / 被核对引用总数，并另外报告缺失引用的事实数 |
| 拒答与误拒答 | 无答案题的正确拒答率与有答案题的误拒答率分别报告；失败请求另计 |
| 时延与成本 | 分别记录检索与整次回答耗时，报告样本数、P50/P95 和平均每问模型成本；小样本 P95 仅作观察值 |

- 页级命中是证据定位的近似指标；同页包含答案但片段遗漏答案时可能高估效果，应在失败分析中说明。
- 标准证据之外的合理支持页面可人工复核，但不得静默修改官方标注；分别记录原始评分与复核说明。
- 记录输入输出 Token、重试与收费调用；区分一次性索引成本和在线问答成本。无法获取费用时报告不可得，不记为零。
- 发布数据版本、配置、模型标识、运行时间、运行环境说明和逐题输出。模型服务存在随机性时说明复现限制。
- 若使用模型辅助评分，保留评分规则并人工复核；不能以模型裁判作为唯一正确性依据。
- 不预设提升百分比。提高、持平或下降均需真实报告，不能仅展示最有利的一组结果。

## 7. 验收标准

### 7.1 功能与可复现性

- 按 README 可完成配置、数据准备、启动演示和运行实验；模型密钥通过本地配置提供，不进入版本控制或浏览器前端。
- 固定输入与配置产生可校验的文档和切分数据；已有有效结果可复用，获取失败有明确提示。
- 至少人工核验 6 条完整演示案例：2 条数值事实、2 条业务或风险事实、2 条无答案问题。所有有答案案例均有正确且可打开的原文引用，无答案案例明确拒答。
- 相关测试通过，服务超时、限流或错误不会显示成成功答案；演示文档与问题的选择范围清晰。
- 在本机输入非预设问题，验证真实检索、生成和证据定位；演示素材来自实际运行，静态结果不能代替本地程序验收。
- GitHub 中的项目介绍、结果与演示素材无需读者配置 API 密钥即可查看；完整复现如需模型服务，应说明配置方法、预期费用与环境要求。
- 本地程序具备输入与输出长度限制、调用超时及费用控制；密钥保存在本地配置，额度不足或服务错误时有明确提示。

### 7.2 实验证据

- 标准首版满足第 5 节数据规模，运行第 6 节三组方案，输出逐题结果和全部必报指标。
- 评测题中答错、无引用、服务失败或被拒答的题目必须保留；不能只统计成功请求而不披露失败数。
- 全体结果均在报告中可追溯，并至少分析 3 个真实失败案例；若固定评测中不足 3 个，则报告全部失败，并将补充压力测试单列。
- 未预设整体正确率门槛。首轮开发集基线用于确定是否需要进一步收缩场景；上述可核验演示门槛和真实评测要求不能豁免。

### 7.3 求职材料

- 交付一个可运行版本、演示素材、结构说明、对比结果、错误分析及简历描述草案。
- 在 GitHub 页面检查 README 的图片、相对链接、结果表和演示入口可读；不得引用开发者电脑的绝对路径作为公开素材地址。
- 仓库提供代表性问答与原文证据截图，以及短录像或 GIF；开发集演示案例与最终评测结果明确区分。
- 区分已实现能力、实验性能力和后续计划；说明评测规模及文档选择范围。
- 项目讲解至少回答：检索如何工作、混合方案为何可能有效、证据如何定位、拒答如何判断、最主要的失败是什么。
- 本规格完成不代表产品已实现；提交、发布与实验完成状态分别记录。

## 8. 六天交付窗口内的范围缩减优先级

目标日期为 2026-09-21（中国标准时间）。以下是时间或资源不足时的删减顺序，不是开发顺序；应尽早验证本机运行与模型资源可行性，预留仓库展示和复现检查时间。

2. 简化本地交互为命令行，使用实际运行录像和证据截图展示；保留可执行的提问、回答与证据定位流程，以及 GitHub 可读的成果入口。
3. 重排降为后续实验；首版保留纯向量与混合检索两组完整对比，明确标记为缩减版，不能宣称完成三组实验。

5. 若仍无法完成，进一步缩小支持的问题类型并重新定义范围；交付明确标记的原型，不能将未达到最低标准的成果称为首版完成。

不可削减：来源可追溯、全文检索而非证据页泄漏、开发与最终评测隔离、真实引用核验、真实实验结果、基本错误处理、本地可运行的端到端流程、可供招聘方查看的 GitHub 成果材料。
